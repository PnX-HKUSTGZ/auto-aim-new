# 下位机通信协议（auto-aim ↔ MCU）

> 与 MCU 对齐的是第 2 节的**新帧族 v1**；第 1 节现有帧保持不变，仅作背景。
> ROS 侧契约见决策仓库 `docs/INTERFACES.md`；位段含义见 `sentry_decision_core/referee_protocol.hpp`。
> 规则依据：RoboMaster 2027 通信协议 V1.0.0 表 1-23（0x020D）与表 1-33（0x0120）。
> 实现状态：上位机（auto-aim）已按 §2 实现帧收发；MCU 侧待实现。

## 1. 约定与现有帧

- 物理层：`/dev/ttyACM0` @ 115200 8N1；串口由 auto-aim 独占，决策 / 导航不直接接触。
- 字节序：全部小端。
- 现有帧（**不变**）：

| 头 | 方向 | 大小 | 用途 |
| --- | --- | --- | --- |
| `0x5A` | MCU → 上位机 | 54 B | IMU / 云台 + 裁判基础字段（血量 / 弹量 / `game_start` 等） |
| `0xA5` | 上位机 → MCU | 28 B | 云台控制 |
| `0xA6` | 上位机 → MCU | 28 B | 底盘速度 |

- 旧 `0xA7`（4 B，仅 `ifreload`）已废弃，由 §2.3 取代。
- 新帧以 `0xAA` 开头，与 `0x5A` 帧按首字节区分、共用同一串口。

## 2. 目标协议 v1（需要 MCU 实现）

### 2.1 帧格式

| 偏移 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | uint8 | `magic` | `0xAA` |
| 1 | uint8 | `version` | `0x01` |
| 2 | uint8 | `type` | `0x01` 上行裁判 / `0x02` 下行决策 |
| 3 | uint16 | `length` | payload 字节数 |
| 5 | uint8[length] | `payload` | 见 §2.2–§2.3 |
| 5+length | uint16 | `crc16` | 小端 |

- **CRC-16/MCRF4XX**：poly `0x1021`（反射 `0x8408`）、init `0xFFFF`、输出不异或、小端；
  覆盖 `version` 到 payload 末字节（偏移 `1 ~ 4+length`）。
- 帧示例（裁判上行，payload 29 B）：`AA 01 01 1D 00 <29 B payload> <crc_lo> <crc_hi>`。
- `type=0x03`（执行回执）**已取消**，保留不复用；MCU 不需要回传任何执行结果。

### 2.2 `type=0x01` 上行：裁判 / 自身（建议 10 Hz，payload 29 B）

| 偏移 | 类型 | 字段 | 单位 / 说明 |
| --- | --- | --- | --- |
| 0 | uint8 | `game_status` | 0 未开始 / 1 准备 / 2 自检 / 3 倒计时 / 4 比赛中 / 5 结算 |
| 1 | uint16 | `game_time_remaining` | s |
| 3 | uint16 | `coin_remaining` | 己方金币 |
| 5 | uint8 | `detect_color` | 红蓝方，编码待确认 |
| 6 | uint8 | `flags` | bit0 `can_rebuild_outpost`，其余保留填 0 |
| 7 | uint16 | `sentry_hp` | 己方哨兵血量 |
| 9 | uint16 | `sentry_ammo` | 剩余发弹量 |
| 11 | uint16 | `our_base_hp` | 己方基地血量 |
| 13 | uint16 | `our_outpost_hp` | 己方前哨血量 |
| 15 | uint16 | `enemy_base_hp` | 敌方基地血量 |
| 17 | uint16 | `enemy_outpost_hp` | 敌方前哨血量 |
| 19 | uint32 | `event_code` | 0x0101 场地事件原始值 |
| 23 | uint32 | `sentry_info_1` | 0x020D 兑换 / 复活原始值 |
| 27 | uint16 | `sentry_info_2` | 0x020D 脱战 / 姿态原始值 |

- `event_code` / `sentry_info_1` / `sentry_info_2`：MCU **直接转发原始字节，不用解析**，由上位机进行解析和处理。
（本版暂不发送：`sentry_info_3`、雷达、队友位置、手动点等）

### 2.3 `type=0x02` 下行：决策命令（payload 9 B）

| 偏移 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | uint32 | `request_id` | 请求序列号，仅用于日志关联；同一目标的重试复用 |
| 4 | uint8 | `kind` | 动作类型，见下表 |
| 5 | int32 | `value` | **协议累计目标值 / 电平位**，见下表 |

以下是 `kind` 字段的取值说明：

| `kind` | 动作 | `value` 语义 | 对应 0x0120 |
| --- | --- | --- | --- |
| 1 | 本地兑换发弹量 | 本场累计已兑换发数（单调递增） | bit 2-12 |
| 2 | 确认免费复活 | 电平：1 确认 / 0 清除 | bit 0 |
| 3 | 兑换立即复活 | 电平：1 兑换 / 0 清除 | bit 1 |
| 4 | 远程兑换发弹量 | 本场累计请求次数（单调递增，每次仅 +1） | bit 13-16 |
| 5 | 远程兑换血量 | 本场累计请求次数（单调递增，每次仅 +1） | bit 17-20 |

- 帧示例（request_id=101、kind=1、累计目标 150）：`AA 01 02 09 00 65 00 00 00 01 96 00 00 00 6A 13`。

**为什么是累计值**：裁判协议本身按「总量」结算，例如 0x0120 bit 2-12 表示「哨兵将要兑换的发弹量值」，
从 0 改到 X 就消耗 X 金币；同一个 X 重复下发不会再扣一次。因此上位机的重试是幂等的，
MCU 不需要按 `request_id` 去重，也不需要判断是否成功。

### 2.4 MCU 侧行为

MCU 维护一份 **4 字节的 0x0120 指令状态**，收到一条决策命令就更新对应字段，并按固定节拍（建议 10 Hz）
把整份状态发给裁判系统：

- `kind=1`：把 bit 2-12 写为 `value`；若 `value` 小于当前值则**忽略**（协议要求单调递增）。
- `kind=4`：把 bit 13-16 写为 `value`；只接受「当前值 + 1」，否则忽略。
- `kind=5`：把 bit 17-20 写为 `value`；只接受「当前值 + 1」，否则忽略。
- `kind=2`：bit 0 = `value`（0 或 1），原样写入。
- `kind=3`：bit 1 = `value`（0 或 1），原样写入。
- 其余位（姿态 bit 21-23、能量机关 bit 24）暂由 MCU 保持默认 / 后续扩展。

> 上面的单调性 / “每次 +1” 检查只用于避免发出协议非法的帧，**不是**在判断裁判是否接受。

不做的事：

- **不回执**、不校验金币 / 脱战 / 增益点，也不判断裁判是否接受——这些由裁判系统裁决。
- 不对 `request_id` 做去重（累计值本身已经幂等）。
- 电平位（`kind=2/3`）原样保持；上位机在复活完成 / 放弃后会再发一条 `value=0` 清零。
- 串口重连 / MCU 重启时把 0x0120 状态清零，避免上一局的电平位残留。

### 2.5 生效校验在上位机

```text
决策 --DecisionCommand--> auto-aim --0x02--> MCU --0x0120--> 裁判
决策 <--0x020D 累计值 / 血量------------------------------ 裁判
```

决策侧发出命令后等待 `action.verify_delay_ms`，再用 0x020D 判断：

- 兑换发弹量：`sentry_info_1` bit 0-10 ≥ 目标值；
- 远程兑换：对应累计次数 ≥ 目标值；
- 复活：`self_hp` 从 0 变为正。

未生效则重发同一目标（同一 `request_id`），最多 `action.max_attempts` 次；仍失败则放弃并记 WARN。
复活动作是电平位，在读条期间按 `action.revive_verify_delay_ms` 持续置位。
